# F.A.C. V2 Firmware

Firmware for the **F.A.C. V2** (Floppy Ant Controller), the antweight combat-robot control board by Floppy Lab
(STM32F072CBT6, Cortex-M0 at 48 MHz). It drives 3 DC motors and 2 HV servo outputs, reads a PWM or PPM RC receiver,
an LSM6DS3 IMU and the battery voltage, and is configured over USB from the [FAC Tool](https://factool.floppylab.it/).

From **2.1.0** the firmware runs under the USB CDC bootloader ([FAC-V2-Bootloader](https://github.com/FloppyO1/FAC-V2-Bootloader)):
updates are installed from the FAC Tool, with no drivers and no ST-LINK.

## In short

- **Signal chain:** receiver → normalised channels → active mix / special functions → mapper → motors and servos.
  Every value along the chain is an integer on `[-1000, +1000]`; there is no floating point in it (the M0 has no FPU).
- **Mixes and special functions:** one mix active at a time (up to 8 inputs, 10 outputs), up to 20 special functions
  running together. Each motor and servo output is linked to one of their outputs from the FAC Tool.
- **States:** `DISARMED` → `NORMAL` → `CUTOFF`. Arming requires a connected receiver and calibrates the IMU;
  `CUTOFF` latches when the cell voltage stays below the threshold.
- **Settings** are stored in the I2C EEPROM and exchanged with the FAC Tool over USB CDC; telemetry (channels,
  battery, state, accelerometer, gyroscope, IMU status) is a 34-byte packet.
- **Motor PWM** is generated in software by DMA into `GPIOA->BSRR`; the motors also play the startup jingles and
  the status beeps.

## Memory layout (with the bootloader)

| Area | Addresses | Contents |
|---|---|---|
| Flash, pages 0–7 | `0x08000000`–`0x08003FFF` | bootloader |
| Flash, pages 8–62 | `0x08004000`–`0x0801F7FF` | this firmware; `"FACA"` header at `0x080040C0` |
| Flash, page 63 | `0x0801F800` | "app valid" record, written by the bootloader |
| RAM | `0x20000000`–`0x200000FF` | vector table copied to SRAM + block shared with the bootloader |

The firmware **does not start on a board without the bootloader**. Debug builds carry a flag in the header that lets
the bootloader start them without the "app valid" record, so building, flashing and debugging over ST-LINK keep
working.

## Repository layout

| Path | Contents |
|---|---|
| `Core/Src/FAC_Code/`, `Core/Inc/FAC_Code/` | application logic (ours) |
| `Core/Src/FAC_Code/mixes_functions/` | mixes, special functions and their templates |
| `Core/Inc/FAC_Code/config.h` | firmware version, thresholds, debug switches |
| `Core/Src/Libraries/` | DMA soft PWM, LSM6DS3 driver |
| `Core/Inc/FAC_Code/fac_boot_shared.h` | addresses and structures shared with the bootloader — **copied unchanged** from its repository |
| `Core/`, `USB_DEVICE/` (outside the above) | generated by STM32CubeMX; our code only inside `USER CODE` sections |

| `docs/` | architecture and API reference |

## Building

Two equivalent builds exist side by side, with the same sources and flags.

**STM32CubeIDE:** import the project (`.project`, `.cproject`), build the `Debug` or `Release` configuration and
flash over ST-LINK.

**VS Code:** install the **STM32Cube for Visual Studio Code** extension (recommended by `.vscode/extensions.json`),
open the folder and accept the CMake preset (`Debug` or `Release`). *FAC V2: build, flash and debug (ST-LINK)* builds,
flashes and stops at `main`. From the command line, with the extension's CMake, Ninja and GCC on `PATH`:

```sh
cmake --preset Release
cmake --build --preset Release
```

The output is in `build/<preset>/`: `FAC_Firmware_V2.elf`, `.hex`, `.bin`.

## Installing

- **Users:** install the release `.bin` from the FAC Tool, which talks to the bootloader.
- **Developers:** flash a Debug build over ST-LINK, on a board that already has the bootloader. A Release build
  flashed over ST-LINK on top of an app installed by the FAC Tool finds a stale record and stays in the bootloader:
  reinstall it from the tool.

## Versioning

`FIRMWARE_VERSION_MAJOR/MINOR/PATCH` in `Core/Inc/FAC_Code/config.h` (MAJOR = breaking, MINOR = backward-compatible
feature, PATCH = fix). The FAC Tool reads it as `major·10000 + minor·100 + patch`. **Any version bump resets the user
settings to their defaults on the next boot.** Releases are tagged `V<major>.<minor>.<patch>`.
